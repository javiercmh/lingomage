# Generation pipeline

How stories, chapters, help and examples are generated, validated, checkpointed and recovered, including background operation sessions. Rationale: [PED-002](../pedagogy/PED-002-contextual-reading-support.md), [PED-003](../pedagogy/PED-003-story-memory-and-paths.md), [PED-004](../pedagogy/PED-004-level-guided-generation.md). Architecture docs: [overview](overview.md) · [data and storage](data-and-storage.md) · [generation pipeline](generation-pipeline.md) · [learner tracking](learner-tracking.md) · [safeguards](safeguards.md). Interface rules: [`DESIGN.md`](../../DESIGN.md).

## Generation

- **Targets** ([PED-004](../pedagogy/PED-004-level-guided-generation.md)): CEFR A1–C2 (German, Spanish), JLPT N5–N1 (Japanese), Elementary/Basic/TORFL-I–IV (Russian). Self-selected orientation, not assessed proficiency. Settings keep explicit selections separate from legacy enablement and self-assessments; no guessed conversion.
- **Inputs:** level, one optional story idea and topics brief, narrative scope (`scene` or `chapter`; saved `longer` reads as chapter), regional and register preferences. No word or sentence quotas.
- **Stages** for Create, Continue and Rewrite: optional bounded vocabulary/grammar plan → validated canonical prose → contextual glossary notes (at least one structurally valid note required) → Japanese readings when kanji are present. Examples skip the plan and notes. Plans guide writing; coverage is not required and no word knowledge is claimed.
- **Note density:** `config.noteDensity` captures Settings → Vocabulary notes (`fewer`, `standard`, `more`) when the operation is created; `notesInstructions(density)` in `js/prompts.js` builds the notes prompt, and an absent value means `standard`. Resume and every split part use the saved value, so changing the setting never affects a running or saved operation. The applied version records it as provenance.
- **Split notes:** with Settings → Split vocabulary notes on (default), `config.notesParts` is captured as `MAX_NOTE_PARTS` (8; else 1), a maximum. After prose, `notesParts()` groups paragraphs into parts of about `noteTargetUnits` (1,000 UTF-16 units, 400 for Japanese), never below 600 or 250 and never more than the maximum (a short tail joins the previous part; a short chapter stays one request). Operations saved earlier with 3 keep at most 3 parts. Parts are saved as `notes-1`…`notes-N` in `op.parallel` with canonical `start`/`end`, beside `readings` for Japanese; a single part keeps the legacy `notes` key or the sequential `notes` stage. Each part sends the whole chapter plus `focus` `{part, of, text}`; a part may validate with zero notes, the merged glossary (`mergeNoteParts`, chapter order, identical headword+explanation joined) must have at least one. A progressive operation (below) first splits off a lead part: the opening paragraph, joined with following ones while under half the minimum; the rest is split as usual within the maximum, and Japanese `readings` is ordered right after it. At most `config.parallelLimit` parts run at once: `parallelLimitFor(concurrentRequests)` gives `MAX_PARALLEL` (6), or 1 with Settings → Allow concurrent requests off; operations saved without it keep 3.
- **Rate limits:** App² sets no request limit of its own; provider limits arrive as `usage_limit`. A part whose start is refused (`usage_limit` or `request_in_progress`, before any inference) waits until a running part finishes and starts again; with nothing running, the operation stops with failure phase `start` and saved parts. A provider `usage_limit` during a request stops new parts, lets running ones finish and save, and sets `op.partsOneAtATime`, so Resume runs the missing parts one at a time. There are no timers and no automatic resends of a request that started; ChatGPT plan quota and rate limit share one code, so the recovery copy says Resume fails again until a quota resets.
- **Broken replies:** a reply that is not valid JSON (`invalid_json` from `parseContent` or `decodePlan`) is resent automatically, up to `MAX_BROKEN_RESENDS` (3) times per stage or notes part, when the operation captured `config.retryBroken` (Settings → Advanced → Retry broken replies automatically, on by default). Resends are announced, never silent: the broken request is invalidated and released first, `op.retried[stage or part]` counts the resend, the pipeline calls `onResend` (the app shows a toast naming the step and "N of 3"), and progress labels the step "· retry N of 3" until it finishes. The fourth broken reply stops with recovery saying how often LingoMage already retried; an explicit Retry then sends one request without further automatic resends. JSON that fails validation is never resent. Checkpoints without `retryBroken` never resend. Explanation, detail and story-memory requests are outside this rule.
- **Light tasks model:** an operation captures `config.light` (`{model, reasoning}` or null) at start, from Settings. The notes and readings stages use it (`stageModel()` in `js/generation-pipeline.js`); plan and prose always use `config.model`. Saved versions record it as `lightModel` beside `model`. Story-memory summaries and condensing (background, Continue/Rewrite preparation, rebuild) use the light model directly, and their memory records name it as `model`. Checkpoints without `light` use the story model throughout. One operation session may carry requests for both models; the host checks the route only at `begin`.
- **Scene vocabulary:** the plan can flag plot-relevant terms and suggest accessible clues in its guidance. The shared prose prompt uses familiar surrounding language and asks for nearby clues for potentially unfamiliar terms that matter at beginner levels.
- **Japanese readings:** after notes validate, the app extracts contiguous kanji compounds from title, story or example sentences with occurrence IDs, UTF-16 offsets and context, requests only kana readings, validates exact ID coverage and builds annotations itself. Kana-only content skips the call. Popover headwords are excluded.
- **Checkpoints:** every validated stage is saved to `data/generation-checkpoints.json` before its request is acknowledged; checkpoints, not settings, are authoritative for unfinished work. Resume reuses saved stages and captured configuration; completed stages never regenerate. Discard cancels and releases any outstanding request and removes progress. Cancel inside LingoMage persists discard intent even before a new request ID returns. It prevents later stages and application of late responses, settles pending starts and parallel parts, cancels/releases outstanding requests, then removes the checkpoint. Completed final content and already saved story memory remain. Cleanup failure retains the checkpoint for explicit Try again, including after reload; this action makes no inference request. External interruptions retain resumable stages, including session_cancelled and ambiguous not_found errors. A failed notes request keeps the prose.
- **Reading while notes are written:** Create, Continue and Rewrite capture `config.progressive: true`. Once the lead notes part is done (Japanese: and its readings are saved), `applyPartial` saves the chapter with the notes finished so far, marked `notesPending`, and `op.earlyApplied` is checkpointed; the app opens or adds the chapter, keeps Cancel in the status bar and counts note parts. Each later notes part saves the growing glossary into the same version (no new version or chapter). The final apply completes it, clears `notesPending` and records timing. A resumed operation whose lead part is done shows the chapter again first. Notes in one request (split off or a short chapter) open only at the final apply. A failed part stops the run with the chapter readable and its notes so far; Resume continues, and Discard clears `notesPending` (keeping those notes) through `discarded`. Saved operations without `progressive`, Examples and notes rebuilds apply once at the end. While the operation runs, other AI actions (Explain, Define) stay blocked as before; the reader refreshes in place, never under an open note or selection.
- **Final application** is idempotent through `operationId` and stable derived IDs; partial prose never appears as a finished story, and a chapter shown early always has its validated prose. No inference retries automatically.
- **Release failures** keep progress, block new generation and offer Resume or Save / finish; `finishRequest()` releases a completed stage without starting the next. A confirmed `not_found` may be released locally (the host already released it). Known limit: the host's atomic start/request-ID persistence gap.
- **Failure metadata:** records keep the legacy `error` string and may add `failure` (`category`, `stage`, `phase`, `code`, bounded redacted `message`). Categories: service, validation, configuration, storage, cancellation, release, internal; no provider cause is inferred. Successful checkpoint writes restore the preceding operation phase, so a subsequent host error is not mislabelled as a storage failure. Cancel and release phases are distinct so cleanup messages can name stopping a running request versus clearing a finished one. In-app cancellation has an explicit generation_cancelled outcome only after cleanup succeeds; error-message wording does not authorize discard.
- **Version changes:** checkpoints from an older prompt or safeguard version stay inspectable but must be discarded, never resumed under new rules; saved stories and provenance are untouched.
- **Recovery identification:** the shortcut notice (only in a reader without the pending operation’s recovery panel) and recovery panel share a task label derived from the saved operation and its destination story. Continue names the next chapter after the captured path’s end, Rewrite names the captured chapter, and Examples names its source chapter. Review unfinished generation opens and focuses that operation’s recovery; it starts no inference.
- **Retry guards:** stale handlers and repeated clicks cannot rerun an operation; Create Retry clears a draft error only when a matching reader draft exists; captured Create fields are restored after preferences load, then frozen. Explanation and detail retries keep the passage and question; failed acknowledgement IDs block new requests until released. Explanation and detail responses use in-memory save recovery (not durable across reload); chapters, examples and readings use durable checkpoints.
- **Host failure reasons:** `response_too_large`, `incomplete`, `timeout` and specific `invalid_request` errors surface their bounded host messages in the recovery summary with sensitive fragments omitted, without placeholder text; generic `invalid_request` errors on checkpoints saved without a model explain that no AI model is selected (and Retry adopts the newly selected Settings model). Continue, Rewrite, Examples and Create all verify an available selected model before creating a checkpoint or calling `ai.start`. Saved legacy `[redacted]` markers are also omitted when displayed; an entirely removed reason uses a generic failure message. Story-context failures without a checkpoint show the same `failureInfo` message with their own explicit retry: Continue or Rewrite before the operation exists ("Submit again to retry"), the background story-context toast ("Continue will prepare it") and Rebuild story memory's dialog, cleanup status and toast ("Resume memory rebuild to retry"). `response_too_large` means answer text exceeds the device limit (at least 4194304 UTF-16 units), not the event stream size. `incomplete` names why the model ended early, such as its output-token limit. `timeout` means connection timeout, 45 seconds without streamed data, or a request exceeding 30 minutes; continuously arriving answers are not subject to a short fixed duration limit. `invalid_response` means a malformed answer, not a size or time limit. LingoMage's own content bounds still apply independently.

## Timing and estimates

- **Measured by LingoMage:** the host reports no request times, so the pipeline stamps `startedAt` just before each `ai.start` (saved on the request in the checkpoint) and `completedAt` when its reply or error arrives, and appends one entry per attempt to `op.timings` (`stage`, `part` for parallel parts, `model`, `reasoning`, `startedAt`, `completedAt`, `outcome`: `ok`, `invalid`, `resent`, `failed`). Cancellation records nothing. The clock is injected (`now`) for tests. Story-context summaries before Continue/Rewrite are timed in `readerAi` (`stage: 'context'`) and passed into the operation as its first entries.
- **Approximate attempts:** a request from an earlier page (reload, rotation) only completes when the new page notices, so its entry is `approximate: true` and its whole step is left out of the saved timing.
- **Saved timing:** `summarizeTimings` (`js/generation-timing.js`) turns the entries into `timing` on the saved version: per step `ms` (busy time of all attempts, overlapping parallel parts counted once, so retries count and a stop-and-Resume gap does not), `attempts`, `model`, `reasoning`, plus `requests` for context and `parts` for notes, and `totalMs`. The story record does not repeat it; versions without it are older or unmeasured.
- **Estimates:** `timingSamples` reads saved versions (malformed timing is skipped); `estimateGeneration` adds up each planned step's median of the newest 20 most similar runs (same model, effort, language, scope and note parts; else same model and effort; else same model), with Japanese notes and readings as the longer of the pair and context as pending summaries (`pendingSummaryCount` in `js/story-memory.js`, condensing not counted) × median per summary. Fewer than 3 similar runs for any step means no estimate. Nothing is shown before starting; while running, `remainingTime` subtracts each step's elapsed time on this page (the same in-memory clock as the step timers, so after a reload it starts again). Estimates make no request and change no prompt, so `PROMPT_VERSION` is unaffected. Presentation rules are in [`DESIGN.md`](../../DESIGN.md#generation-status-and-recovery).
- **Ready notifications:** after the result is saved (or a run stops), `notifyWhileAway` posts a host notification only when `notifyWhenReady` is on, the page is hidden and permission is granted. Saving is driven by the host's completion message, so it also happens off screen; Android can still stop work between steps, so the copy never promises completion.

## Validation and bounds

- Shared validation for creation, continuation, rewrite and examples. Japanese without romaji; Russian Cyrillic without transliteration; Russian stress absent unless requested (prompt guidance, not a validator ban). Details in the [safeguard register](safeguards.md).
- Bounds: chapter content 30000 UTF-16 units; total response and assembled content 1000000; per-field maxima for title, notes, forms and examples; at most 20 forms per note; no cap on note count. Validators do not certify linguistic accuracy, complexity or learning effect.
- Glossary validation checks every exact occurrence (repeated forms cached); display links only the first eligible occurrence of each normalized headword/meaning after overlap resolution, processing candidates by form length without materializing duplicates. A shorter listed form inside a longer chosen phrase keeps its own note. A note opened from text leads with the exact matched wording (which Listen speaks) and shows the dictionary headword after it when different.
- Saved content is never revalidated or rewritten on load.

## Reader, memory and help

- Canonical text is kept separate from ruby for selection, copy and speech.
- **Define:** one `define` request through `readerAi` with the light tasks model (`lightTaskConfig`, else the story model) and `DEFINE_INSTRUCTIONS`, sending the chapter, selection offsets, passage, sentence and profile. `validateDefinedNote` runs the chapter-note repair and keeps the note whose forms overlap the selection, else fails validation. The note is appended to the version's `glossary` through the same save-before-acknowledge path as explanations (in-memory save recovery, not durable across reload). No automatic resend; failures offer Retry in the note popover.
- Memory: summary chunks of 2000 estimated tokens (language-aware; about 8000 characters of German, 2000 of Japanese). Memory version 3 is an event graph with code-assigned ids (characters, facts, threads, events with causes and `knownBy`, beliefs, arcs); each `summary` request returns only changes, which code checks and merges. Above 10800 characters a separate `memory-compact` request condenses enough unprotected events into arcs to approach 7200, with source excerpts and `maxArcTextCharacters` (source arc and event text length minus one, the shorter-than-source check), saved as its own record. No request is made when less than 1500 characters could be condensed. An answer that fails its checks is released and the operation continues with the full memory, making no further compaction request in that run; cancellation, storage and service errors still stop. Answers over 30000 characters are rejected; rules in PED-003, bounded recent prose, all lineage-specific. Rewrites include the current chapter as source but exclude its events from preceding context. Removal prunes only unreferenced versions, help and memory. Continue (and Rewrite after chapter 1) summarizes every not-yet-summarized chunk of the earlier chapters before the operation exists, one sequential `summary` request per chunk; usually that is at least the newest chapter, so it is the first, often slow step and Create has no equivalent. The progress checklist shows it as Story context (`hasStoryContext` in `js/generation-progress.js`). With `backgroundStoryContext` on (default), `showOperationResult` queues the saved path and `maybeStartBackgroundContext` runs the same `prepareStoryMemory` once nothing else is live or showing: plain `summary`/`memory-compact` requests without a session (a hidden page pauses with `background_paused`), each record saved before release as usual. `storyContextReady` skips it when the lineage is already summarized. Other AI entry points call `stopBackgroundContext`; Continue and Rewrite call `settleBackgroundContext`, which waits when the run's lineage is a prefix of theirs. A stopped run makes no further request (`config.signal`).
- Memory cache keys use `MEMORY_VERSION` and the memory prompts' own versions (`SUMMARY_PROMPT_VERSION`, `COMPACTION_PROMPT_VERSION` in `js/story-memory.js`), not `PROMPT_VERSION`, so other prompt changes keep saved summaries. Increment the matching constant when a memory prompt changes. Saving a record drops records of another `MEMORY_VERSION`.
- **Rebuild vocabulary notes** (reader menu): an operation of kind `notes` saves the viewed version's canonical `prose` and `languagePlan` as `plan`, and starts at the notes stage (`enrich` with notes parts only when split): no plan, prose or readings request, so Japanese segments stay. It uses the current `noteDensity`, `notesParts` and light choice. Application finds the target version, refuses if its title or story changed, replaces generated notes, keeps Define notes and records `notesRebuild`; re-applying the same operation is a no-op. Recovery, Resume, Discard and checkpoint rules are those of every operation.
- **Light tasks:** `config.light.tasks` (Settings → AI models → Light model → Use it for) decides which steps use the light model: `stageModel` maps the notes and readings stages, and the prose stage of an examples operation, to their task; plan and story prose always use the main model. A saved `light` without `tasks` keeps the earlier behaviour (notes and readings). Requests outside the pipeline use `lightTaskConfig(state, task)`: story memory (`memory`), Define (`notes`), Explain and More detail (`explanations`).
- **Rebuild story memory** (reader menu): clears the story's memory records and saves a `memoryRebuild` marker with the captured path and entries in one write (restored if the write fails, before any request), then runs `prepareStoryMemory` for that lineage inside `aiSession.run` with the current model. All paths are cleared because shared prefixes depend on the rebuilt graph; chapters, help and generation provenance are untouched. Each record saves before release; an unfinished rebuild resumes from saved records, also after reload, and clears its marker when done. Removing the captured lineage clears the marker. Typical use: rebuilding with a newer model, since records are not keyed by model.
- Initial help returns UTF-16 excerpt boundaries in the source, an optional English context translation and one short explanation. Detail returns plain text (legacy JSON accepted). Examples return three canonical sentences with English translations and validated highlight ranges; Japanese readings use the staged pipeline.

## Background operation sessions

A running request continues in App²'s native service in the background. Android can freeze WebView timers after about 60 seconds off screen, while host messages and the promises they resolve still run. `ai.wait` subscribes to the host's pushed `complete` and `error` messages so validation, checkpoint saving, acknowledgement and the next `ai.start` proceed without timers. Its 400 ms poll remains a fallback and the only completion path for persisted request IDs from an earlier page. LingoMage holds one operation session (`js/ai-session.js`, host `ai.sessions`) across multi-request operations because Android restricts starting a foreground service from the background.

- A session is a bounded hold on the host service, begun with the first request's provider and model (same AI permission as `ai.start`). It starts no inference and does not keep the page running; if web steps stall, the checkpoint stays at its stage for Resume.
- Opened lazily at the first `ai.start` in a scope; ended when the outermost scope finishes. The host also ends it after about 90 s without a running request (on the released host whether on or off screen; on App² Dev 18+ only while on screen), after 30 minutes, at Android's foreground-service limit, on notification Cancel, AI revocation, or page replacement. The app never reopens an ended session, with one exception: when a start is refused with `session_idle` (the host released the session during a gap between steps before any inference) and the page is visible, that start opens a new session and is sent once more. A second refusal, a hidden page or any other session end stops the operation; only the next explicit Create, Continue, Rewrite, Examples, Resume or Retry opens a session. Idle recovery says work was released after a pause without a running step, without assuming a host-specific duration.
- Scope: Create (plan, prose, notes, readings); Continue and Rewrite including the story-context summary requests (`readerAi` joins the outer scope and never ends it); Examples; Resume.
- Finish request, Save response, acknowledge, release and discard never open a session or probe capabilities. Resume with an outstanding request polls, saves and acknowledges first.
- Editing a saved follow-up uses the same detail request with the original explanation and earlier detail entries as context. The generated replacement stays available for save retry, and the request is acknowledged only after the story save.
- Single requests (Explain and follow-ups) use no session, but every `ai.start` uses the wrapper: a hidden page without a session makes no host call and pauses with `background_paused`.
- Stage transitions, memory summaries and compaction, parallel-part scheduling (Japanese readings and split notes) and the session wrapper use promises without timer delays. UI timers and animation frames do not gate active operations; the AI bridge's 30-second command timeout only bounds a reply wait. Optional background story-context preparation starts after Ready clears, remains unsessioned and can pause before its next request when hidden.
- Old hosts: the wrapper asks `capabilities` once and caches only `{sessions:1}` or exactly `invalid_request` "Unsupported AI command."; timeouts, other errors and malformed answers reject. A `sessions.begin` without a usable bounded `sessionId` is an error. `dev_server.py` answers like an old host, so sessions are tested offline here (`tests/ai-session.mjs`) and on devices in App².
- Rotation loads a new page that cannot hold the old session; the host releases it while the request continues, and the new page polls, saves and acknowledges by saved ID. Closing the task cancels both.
- Stored diagnostics redact session, request and account IDs.
- Background-stop recovery and error presentation guidelines are in [`DESIGN.md`](../../DESIGN.md#generation-status-and-recovery); `js/generation-errors.js` supplies the shared reasons. Diagnostics omit sensitive fragments and legacy redaction markers without placeholder text.
