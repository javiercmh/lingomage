# Architecture overview

What the app is made of: platform, modules, version constants and tests. Architecture docs: [overview]() · [data and storage](data-and-storage.md) · [generation pipeline](generation-pipeline.md) · [learner tracking](learner-tracking.md) · [safeguards](safeguards.md). Interface rules: [`DESIGN.md`](../../DESIGN.md).

## Overview

- Dependency-free HTML/CSS/JavaScript App² subapp at the repository root; no build step, framework, native code or production server. Historical Kotlin is in Git; the [safeguard audit](safeguards.md) records what was adopted.
- `dev_server.py` (Python 3.12+) serves the workspace for browser testing with deterministic `--mock-ai`, or development-only `--chatgpt` through the Codex CLI login (Codex runs with a private `CODEX_HOME` holding only the sign-in, so user-level Codex instructions never enter requests).
- Prompts: every AI prompt and `PROMPT_VERSION` live in `js/generation/prompts.js` (story and chapter prose, Explain/More detail/examples, language plan, vocabulary notes, Japanese readings). Only the story-memory prompts stay in `js/generation/story-memory.js` with their own versions.
- Versions: prompt `PROMPT_VERSION` in `js/generation/prompts.js`, safeguards `SAFEGUARD_VERSION` in `js/generation/learning-validation.js`, memory `MEMORY_VERSION` and memory prompts `SUMMARY_PROMPT_VERSION`/`COMPACTION_PROMPT_VERSION` in `js/generation/story-memory.js`, app `version` in `manifest.json`.

## Modules

`js/app.js` and `js/bridge.js` sit at the top of `js/` (the App² template layout); every other module lives in an area folder.

- `js/bridge.js`: the only caller of host APIs (`ai`, `speech`, `translation`, `share`, `updates`, `selectionMenu`, files). App² owns AI configuration and credentials (App² Settings → AI), speech, translation and update installation; the workspace never stores credentials or request headers.
- `js/app.js`: start-up and composition only: constants and level/scope helpers, `state` (grouped by area), the shared `runtime` bindings, storage and settings saving, toasts and views, then one `create…(deps)` call per module in their original top-to-bottom order, and the boot sequence.
- `js/core/`: `workspace-storage.js` (store definitions, validators, missing/valid/invalid states), `settings-controls.js` (what settings load into state, the save transaction, keeping Settings controls in line), `settings-feedback.js` (preference-save notices, reload guard), `ai-session.js` (the `ai.start` wrapper and operation sessions), `ai-notification.js` (task-specific `title`/`body` for every `ai.start`; presentation only), `request-lifecycle.js`, `light-model.js` (light-task model choice), `selection-menu.js` (host selection-menu routing), `story-model.js` (legacy chapters and exact-version paths).
- `js/generation/`: pipeline and rules: `generation-pipeline.js` (staged generation), `generation-controller.js` (idempotent final application), `generation-errors.js` (failure categories, recovery wording), `generation-timing.js` and `generation-progress.js` (pure helpers), `prompts.js` (every prompt except story memory, `PROMPT_VERSION`), `learning-validation.js` (`SAFEGUARD_VERSION`), `story-memory.js` (bounded lineage memory), `story-generation.js`. Generation UI: `generation-bar.js` (the one status record and its bars, Ready countdown, swipe to dismiss, the bar's action), `generation-status-ui.js` (waiting screens, estimates, ready notifications), `checkpoint-recovery.js` (progress cards, generation locks, recovery panels, resuming, starting an operation), `generation-results.js` (early and final results, announced resends, creating the pipeline), `background-context.js` (story memory prepared while reading), `model-settings.js` (Settings → AI models).
- `js/reader/`: `reader-view.js` (opening the reader, chapters and paths, navigation, panels and preferences, note cards, reading location), `reader-controls.js` (⋮ menu, removal dialog, resizing, chapter and storyline pickers, previous/next, furigana), `reader-selection.js` (selection toolbar and its actions), `reader-listen.js` (title fit and chapter listening), `help-cards.js` (story-text activation, saved explanations with follow-ups and examples, explanation selection, loading and chapter status cards), `reader-requests.js` (`readerAi`, saving or releasing pending responses, Explain), `define-note.js` (Define), `continue-flow.js` (Continue and Rewrite), `story-rebuild.js` (rebuild story memory or vocabulary notes), `reader-player-ui.js` (sentence player controls); helpers `reader-text.js`, `reader-activation.js`, `reader-panels.js` (nonmodal panels), `reader-player.js`, `reader-speech.js`, `paragraph-gaps.js` (display only).
- `js/screens/`: `create-flow.js` (Create), `library-view.js` (Library cards, Story Actions, long press, deletion), `library-selection.js` (selecting several stories), `library-activity.js` (ordering and dates), `share-dialog.js` (Share, including opening it, and Import story), `story-share.js` (pure text formatting, export, import validation; only `js/bridge.js` accesses `AppShare`), `stats-view.js` (Stats and Most looked up), `language-settings.js` (learning-language rows).
- `js/tracking/`: `usage-tracker.js`, `usage-stats.js` (time tracking), `consultation-signals.js`, `reading-exposure.js` (lookup history and probable reading), `learner-tracking.js` (wiring them to the reader).

### Module convention

- A UI module exports one `create…(deps)` factory. `js/app.js` calls the factories in a fixed order, so listeners register and start-up runs in the same order as when the code lived in one file. Per-boot state stays inside the factory (the test harness boots `js/app.js` several times per process).
- Bindings that several modules read and reassign (`pipeline`, `readerGeneration`, `creatingStory`, `backgroundRun`, `playbackContext`) live on the `runtime` object created in `js/app.js`; modules read and write `runtime.x` and never keep a copy. Bindings internal to one module that another module changes go through a setter it exports (`js/reader/reader-view.js` exports `setReaderViewport` and `setRestoringPathPosition`, which `js/reader/reader-controls.js` calls on resize and storyline changes).
- A factory receives its dependencies when it is created. A function from a module created further down is passed as a call-time wrapper `name: (...args) => name(...args)`; an object created further down needs a forwarder (see `selectionMenuRouter` for the reader). Do not reassign a dependency on the deps object after creation: the factory has already destructured it.
- Modules import pure helpers and `js/bridge.js` directly; everything that belongs to another factory comes through `deps`.
- Order exceptions to "where the code used to be": `createReaderPlayerUi` runs just before `createReaderSelection` (the player once sat inside the reader-help section); the selection actions register with the selection toolbar rather than after Define. The moved listeners share no target and event type with the code they now precede.
- A new module goes in `manifest.json` (`files` and `app2Update.managedFiles`; `scripts/check.py` fails otherwise) and, if any test reads its source text, in `MODULES` in `tests/support/app-source.cjs`.

### Tests and module source

- New tests run a factory directly: `tests/support/factory-harness.mjs` loads a module with `js/bridge.js` replaced by `tests/support/fake-bridge.mjs`, gives every dependency a test does not name a no-op default (`deps()`; `deps(given, { strict: true })` throws instead, for tests whose point is which callbacks run), and offers a stub DOM (`stubDom()`). Examples: `tests/background-context.mjs`, `tests/ai-exposure.cjs`, `tests/memory-rebuild.mjs`, `tests/continue-stays-put.cjs`, `tests/generation-recovery-regression.mjs`.
- Older tests read source text through `tests/support/app-source.cjs` (`js/app.js` plus every UI module, factory wrappers and indent removed). Whole-source invariants (for example, every `ai.start` goes through `aiSession`) stay there on purpose. Some older tests still evaluate slices between text markers; a module those tests slice must keep the marker functions in one file and in order, and its code must stay free of multi-line template literals. `MODULES_SLICED` in that helper lists those modules; any other module can be restructured freely. Migrate a slicing test to the factory harness before restructuring its module.

## Testing

- `python3 scripts/check.py` (Node 22.15+, Python 3.12+) runs every Node and Python test. It runs the first `node` on PATH and prints its version.
- Node versions: 22.15 is the supported minimum (tests `require()` ES modules, and `tests/support/factory-harness.mjs` uses `module.registerHooks`). A machine can have several Node versions, and `check.py` does not choose among them. With Homebrew, the `node` formula (currently 26) owns `node` on PATH, while `node@22` is keg-only: installed but not on PATH, so a plain `check.py` run tests Node 26 even though Node 22 is installed. To test on Node 22, put its keg first: `PATH="$(brew --prefix node@22)/bin:$PATH" python3 scripts/check.py`. Other projects on the same machine call `/opt/homebrew/opt/node@22/bin/node` directly for the same reason. Run both versions after changing test tooling.
- `python3 scripts/browser_smoke.py` prints a runner URL; Run smoke checks needs its disposable-workspace marker and offline mock. It covers the four language flows, notes, reopening, continuation and rewrite, cancel/reload/resume, malformed and blank stores with Retry loading, unreadable settings and injected settings write failures. `tests/browser/inspect.html` gives screenshot fixtures for recovery and write-failure states. `tests/app-startup.mjs` boots `js/app.js` against a stub DOM. `tests/support/factory-harness.mjs` runs a single module factory (see [Tests and module source](#tests-and-module-source)).
- Mock fixtures establish interface and contract behavior only. Host (Android) behavior is tested in App², not here; live-model evidence is in the [generation test results](../evaluation/generation-tests/results.md).
