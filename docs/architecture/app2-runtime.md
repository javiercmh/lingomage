# App² subapp runtime

LingoMage is a dependency-free HTML/CSS/JavaScript App² subapp at the repository root. `dev_server.py` provides Python 3.9+ browser testing with deterministic `--mock-ai` responses or optional development-only `--chatgpt` through the Codex CLI login. There is no native LingoMage app, Gradle build or production Python service. Historical Kotlin source remains in Git; [the safeguard audit](language-safeguards.md) records what was adopted, adapted and rejected.

## Current level-guided generation (2026-10-13)

[PED-004](../pedagogy/PED-004-level-guided-generation.md) governs standardized reading targets: CEFR A1–C2 for German/Spanish, JLPT N5–N1 for Japanese and Elementary/Basic/TORFL-I–IV for Russian. Targets are self-selected orientation, not assessed proficiency or certified alignment. App-authored definitions live in `data/learning-profiles.json`. Settings persist explicit standardized selections separately from legacy language enablement and self-assessments; no guessed conversion runs. New requests omit the old freeform knowledge field and preserve regional/register preferences.

Create, Continue and Rewrite use the same frozen input/configuration and checkpoint pipeline: bounded optional vocabulary/grammar plan, validated canonical prose, contextual glossary notes, then app-owned Japanese readings when kanji are present. Examples skip language planning and use the prose/readings pipeline. Narrative scope (scene/chapter; the retired `longer` value in saved records reads as chapter) replaces numerical word/sentence quotas. Technical bounds remain enforced. Plans guide writing but do not require coverage or claim individual word knowledge. The current prompt version is declared in `js/app.js`, safeguard version in `js/learning-validation.js`, and app version in `manifest.json`.

## Ownership and data

Only `js/bridge.js` calls host capabilities. App² owns production AI configuration, credentials, speech, device translation and update installation. Choose providers/models in App² Settings → AI; the workspace never stores credentials or request headers.

- `data/stories.json`: canonical stories, ordered chapters, immutable alternate versions and paths, rolling memory and version-scoped explanations/examples. Old one-story records are interpreted additively and keep their provenance.
- `data/settings.json`: models/reasoning, language enablement, standardized reading targets, retained legacy self-assessments, regional preferences and reading preferences.
- `data/generation-checkpoints.json`: at most one unfinished content operation, seeded empty. Captures ID, kind, destination/path lineage, learner input, prompt and safeguard versions, AI configuration, scope, stage, validated language plan/content and outstanding request ID. No credentials are included.
- `data/learning-profiles.json` and `data/language-safeguards.json`: shipped managed definitions.

Manifest ownership distinguishes managed definitions/code from user data. Packaging seeds empty user defaults, never local stories/settings/checkpoints.

## Content and learning

The production prompt uses standardized reading targets, one combined optional story idea and topics brief, language plans, narrative scope and regional preferences. Every chapter requests learning/practice material and useful English notes even when practice is blank. At least one structurally valid note is mandatory. Notes stay integrated as underlined exact chapter forms opening contextual popovers; headword presentation is unchanged.

Shared content validation applies to creation, continuation, rewrite and examples. Target-script checks enforce Japanese without romaji and Russian Cyrillic without Latin transliteration. Russian stress is absent by default but permitted when requested; intent is prompt guidance, not a categorical validator ban. Correct orthography and natural grammar are requested without the former beginner curriculum restrictions. Definitions and limitations are in [the safeguard register/audit](language-safeguards.md).

Numerical chapter-length quotas are retired under PED-004 and LANG-001. Canonical chapter content retains a 30000 UTF-16 technical bound; title, notes, forms and examples retain their respective structural bounds. Scope is narrative prompt guidance and does not certify complexity or semantic compliance.

## Japanese readings and recovery

For stories first save the optional language plan, then generate and validate canonical prose and checkpoint it before requesting contextual notes. After note validation, the app extracts contiguous kanji compounds from title/story or example sentences, with occurrence-specific IDs, UTF-16 offsets and context, and requests only kana readings. Validate exact ID coverage and construct annotations in the app. Kana-only content skips the reading call. Popover headwords are excluded.

Every validated stage is persisted in `data/generation-checkpoints.json` before acknowledgement; checkpoint storage, rather than settings, is authoritative for unfinished operations. Final story application is idempotent via `operationId`; partial prose never appears as a completed story. Resume reuses saved stages and captured configuration. Discard explicitly cancels/releases any outstanding request and removes progress. Cancellation stops subsequent stages. No inference automatically retries. Save/release failures retain recoverable progress, block new generation and offer explicit Resume or Save / finish. A confirmed `not_found` request may be released locally after a host/server restart; other release failures remain actionable. Malformed checkpoint files block generation rather than silently replacing data.

Checkpoint persistence provides recovery across page recreation, unlike the earlier in-memory-only completed-response workflow. Definitions from an older prompt/safeguard version must be discarded rather than resumed under changed rules. Checkpoints contain learner text and must be treated as user data.

## Reader, memory and help

The full-screen reader keeps canonical selection/copy/speech separate from ruby, with adjustable size, opt-in notes, path/chapter navigation, continuation and alternate rewrites. Existing stories and explanations are not revalidated or rewritten on load.

Narrative memory remains bounded and lineage-specific: 8,000-unit summary chunks, a 12,000-unit serialized memory cap, and bounded recent prose. Rewrites include the current chapter revision source but exclude its events from preceding context. Summary stages preserve the existing save-before-acknowledgement workflow. Removal prunes only unreferenced versions/help/memory and preserves shared path content.

Initial contextual help returns source UTF-16 excerpt boundaries, optional English context translation and one concise explanation. Detail returns plain text with legacy JSON compatibility. Examples return three canonical sentences, English translations and validated highlight ranges; Japanese readings use the staged pipeline. Existing follow-ups retain history and provenance.

## Verification

Run `python3 scripts/check.py` with Node 22 and Python 3.9+. Browser checks use disposable workspace copies because the server saves JSON files. Mock fixtures establish interface/contract behavior only. Native App² insets, selection, speech, device translation, install/update and live AI require separate device checks. Linguistic accuracy, concept novelty and learning effects are not certified by validators. See the [device checklist](../validation/device-checklist.md) and [generation evaluation summary](../validation/generation-evaluation/summary.md).

Glossary validation checks all exact occurrences, while display selects only the first eligible normalized headword/English-meaning identity after overlap resolution. A shorter listed form wholly inside a longer chosen phrase keeps its own tappable note (the longer phrase's note remains on the rest of its text), and a note opened from text leads with the exact wording matched in the story, which Listen speaks, and shows the dictionary headword afterwards when it differs. Cross-annotation Japanese fragments share one popup and one keyboard control. Later words remain selectable for Explain. Cancel persists intent even before a new ID returns and checks it before waits and stage handoffs. Final application uses stable operation-derived IDs to prevent duplication. The host atomic start/request-ID persistence gap remains a limitation. Historical operation definitions remain visible in recovery; Resume rejects incompatible versions with an explicit Discard/new-generation message, without deleting saved stories or altering their provenance.

Chapter Copy/Listen, floating selection actions, device Translate, generation status, provider exposure discovery and publisher identity `com.wynh.lingomage` are preserved from the newer main branch.


New chapter generation checkpoints planning, canonical prose, contextual vocabulary notes, and Japanese readings separately, before releasing each successful request. Prose validation does not require notes until the notes stage; completed chapters still require validated nonempty exact-form notes. Failed note requests retain prose and expose explicit Retry/Discard. The saved-story schema is unchanged. Examples omit planning and notes. Older prompt/safeguard checkpoint versions remain inspectable and require explicit discard to start with current definitions.

Total AI response and assembled content size is bounded to 1000000 UTF-16 units. The glossary has no fixed count cap; nonempty notes, exact attested forms, 20 forms per note and field maxima remain required. The reader groups repeated forms and processes matching candidates one form-length group at a time, retaining longest-overlap and first-occurrence behavior without allocating all duplicate candidates. Validation checks the first eligible exact occurrence and caches repeated form checks. Existing saved records retain their original data and provenance.

## Generation failure recovery — 2026-10-14

Checkpoint records retain their legacy `error` string and may add `failure` metadata (`category`, `stage`, `phase`, `code`, bounded/redacted `message`). Older records remain readable. The error presenter distinguishes service, validation, configuration, storage, cancellation, release and internal errors without inferring a provider cause. No prompt or safeguard changes are included.

Create Retry requires an existing reader draft before clearing a matching draft error: two absent story IDs must not imply that a reader draft exists. Stale operation handlers and repeated Retry clicks cannot run an operation again. Captured Create fields are restored after preferences and picker initialization, then frozen while its checkpoint exists. Completed stages remain durable before release and final application remains idempotent. `finishRequest()` releases an outstanding completed stage without advancing to another inference stage; the learner then explicitly resumes progress.

Reader explanation/detail retries retain their selected passage and question. Failed acknowledgement IDs remain tracked and block subsequent requests until release succeeds; `not_found` means the host has already released the request. Save and release recovery panels are replaced rather than accumulating duplicate previews. These explanation/detail responses retain the existing in-memory save-recovery mechanism; reload durability for them is not newly promised. Chapter, example and Japanese-reading checkpoints retain their existing durable recovery.

## Storage boundaries and controller modules

`workspace-storage.js` owns missing/valid/invalid states for stories, settings and generation checkpoints. A missing file uses its declared seed default; an existing blank file, malformed JSON, incompatible minimum shape or failed read blocks writes to that store. No reset or repair happens automatically. The persistent Workspace needs attention panel names the affected file; Retry loading reloads the workspace after the file has been repaired externally, and refuses while an AI request, an unsaved response or an unsaved preference would be lost. A file is treated as missing when the host reports `ENOENT`, “not found” or “does not exist”, or reads empty while `listFiles` omits it; native read and listing behavior is unverified. Generation is blocked while any required store is invalid, and Settings become read-only (disclosure still works). Other valid stores remain readable, including saved stories when settings are damaged.

Validation checks the shape needed to read records; it does not revalidate or rewrite saved learning content. Optional story fields written as `null` by older versions are accepted as absent. Unknown story fields and unknown settings fields survive subsequent saves: top-level keys, `readingPreferences` keys, and entries inside `targetLanguages`, `standardizedLevels`, `learnerProfiles`, `languageExpectations` and `languageOrder` that this version does not load (future languages, retired level IDs) are written back unchanged, as are legacy values (for example an out-of-range text size or a profile longer than 600 characters) the learner has not changed. Runtime state never holds those values. A known entry the learner removed is not restored. Save failures carry a code: `store_invalid` (unreadable store, never written), `invalid_data` and `write_failed`. A failed write restores the last saved preference snapshot, syncs every affected control (including Listening speed, Follow and the Reasoning options for the saved model) while keeping focus and uncommitted typing, and keeps the intended change so Retry save repeats exactly that change; fields the learner changed since are left alone. `settings-feedback.js` renders the persistent notice in the page and inside the modal reader and never rebuilds it for an identical failure. Checkpoint recovery panels are rebuilt only when their content changes. Historical checkpoint records always carried `kind`, `language`, `config`, `input` and, once a request existed, `request.id` (and `target` for non-create kinds), so the stricter checkpoint validator is not known to reject earlier records; a record that fails it blocks generation and is preserved for manual repair. The development server writes to a same-directory temporary file, flushes it, then replaces the destination; native App² write atomicity remains unverified. This does not close the host start/request-ID persistence gap.

`story-model.js` interprets legacy chapters and exact-version paths; `story-memory.js` owns bounded lineage-specific memory; `generation-controller.js` applies final results idempotently; `reader-panels.js` owns nonmodal panel positioning, focus and listener initialization/disposal; `settings-feedback.js` owns preference-save notices and the reload guard. `story-memory.js` exports the single `MEMORY_VERSION` used for cache keys and saved version provenance. Dependencies are injected so behavioral tests can import production controllers. `app.js` still composes the UI, help, speech and request flows; these extractions do not introduce a framework or change saved formats. Unused competing generation/validation helpers have been removed; regression assertions exercise the production pipeline and validator instead.

Run `python3 scripts/browser_smoke.py`, then open the printed runner URL and select Run smoke checks. The runner only operates with its disposable-workspace marker and offline mock enabled. It covers all four language flows, notes, saved-story reopening, continuation/rewrite, explicit cancellation/reload/resume, malformed and blank stores with a real Retry loading click, readable stories while settings are unreadable, read-only Settings, injected settings write failures (rollback of controls, focus, typing, Retry save, stable recovery panels) and nested-settings preservation. It was extended without being run in a browser by the author of the extension; run it before relying on it. `tests/browser/inspect.html` (same server) adds repeatable screenshot fixtures for the unreadable-settings, in-reader write-failure, Settings write-failure and blank-stories states. `tests/app-startup.mjs` boots the real `js/app.js` against a stub DOM and in-memory files to cover start-up order, store states, the Retry loading guard and the settings rollback/retry wiring in Node. It does not establish screenshot quality, Android behavior or semantic accuracy; inspect screenshots separately at desktop/mobile widths and enlarged text.

The reader preference notice reserves scroll space from its measured layout height, including on resize, so the end of a long chapter can scroll above it. The disposable Write failure in reader fixture checks final-action clearance as well as retry visibility.
